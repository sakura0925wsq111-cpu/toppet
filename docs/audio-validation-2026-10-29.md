## 本轮已确认

- 用户重新接入设备后，硬件识别最初使用 Whisper `base`，短句可返回空字符串。用户观察到设备思考后回待机，文字未进入 qq-bridge。
- 真实录音前约 80～140 ms 出现两次满幅启动脉冲，后续语音很轻。忽略启动区后，两段录音整体 RMS 约为满幅的 0.0005；脉冲掩盖了有效语音的实际电平。
- 同一段“我今天有点累”的录音，原解码不能可靠得到正文；抑制孤立启动脉冲、去除低频偏移并有上限地提升电平后，`small` 模型识别出了正文。
- 原两段真实录音各重复识别三次，六次均为“你好”或“我今天有一点累”，单次约 1.1 秒。数字静音返回空，不生成文字。
- 用户随后在真实设备上重新按键，两句均正确识别，沿当前 qq-bridge、专用 DSH、DeepSeek、Qwen 和无线设备返回回复；设备分别上报播放完成，用户确认“能回复”。

## 修改

### 识别

`audio/asr/whisper_asr.py` 增加针对有界按键录音的预处理：仅抑制最初 200 ms 内短暂、孤立的满幅脉冲，不直接裁掉录音开头；去除 70 Hz 以下偏移，用稳健峰值估计增益，上限为 40 dB，并限制最终峰值。原始录音不被改写。数字静音 / 极低能量输入不强行解码。

硬件默认改用本地已有的 `small` 模型、beam=5、中文解码；继续不做二次 VAD 裁剪。保留移除诱发空录音幻觉的 `initial_prompt` 改动，并过滤高无语音概率片段。优先读取 D 盘完整模型缓存，避免已有模型仍要请求远端元数据。

### 主机稳定性

先前有一次主机以 `-1` 退出，未取得足以证明原因为原生库崩溃的系统报告；同时观察到多次不同启动器的重启。该历史退出原因仍未确证，不能称为已定位到 CTranslate2。

新增 `IsolatedWhisperEngine` 和私有 stdin/stdout 识别进程，复用原 Whisper 实现。主机不再直接加载硬件路径的 CTranslate2 模型。每轮识别有 20 秒结果等待上限；工作进程退出或超时只让当前轮失败，关闭所属进程，下一轮重新启动。失败输入不伪造转写、不提交旧模型任务，不取消 QQ 会话。

自动化测试验证了识别进程退出后的下一轮恢复、超时回收及静音处理。启动脚本启用 Python faulthandler，并在进程退出时将时间与退出码写入 D 盘 `logs/host-exit-*.json`。这些防护不意味着可以阻止其他程序主动结束主机。

### 诊断

`TOPPET_AUDIO_CAPTURE_DIR` 是显式启用的本地诊断开关；默认不录制。拒绝相对路径或解析到 C 盘的目标。保存原始麦克风 PCM、识别文字、Qwen 原始流和最终设备 PCM；诊断写盘失败不阻断聊天。文件名由轮次键散列生成，原始会话信息仅在本地元数据中。

本轮启动时显式开启了该开关，数据位于 `D:\toppet-v2-text-20261022\artifacts\audio-validation-20261029\captures`。普通项目启动不自动继承本轮的录音开关。

### 扬声器增益：已部署并经用户复测

现有固件 `es8311_voice_volume_set(..., 85, ...)` 通过当前驱动换算为 `reg32=0xD8`。根据 [ES8311 User Guide 第 29 页](https://files.waveshare.com/wiki/common/ES8311.user.Guide.pdf)，`0xBF` 是 0 dB，每级 0.5 dB；因此当前设置是 **+12.5 dB**，不是普通的“最大音量的 85%”。

若不启用额外的动态范围保护，刚才两份设备 PCM 在该增益下，约 0.8% 和 3.8% 的采样预计超过满幅。这是根据音频与配置计算出的过载风险，不能冒充扬声器声学实测。

本轮先使用主机端 `TOPPET_SPEAKER_GAIN_DB=-12.5` 抵消这段额外增益，仅用于新硬件聊天输出；没有更换克隆声线或刷固件。健康检查会显示实际补偿值。该设置默认由 `start-qwen.ps1` 为当前板卡配置；以后若把固件 DAC 调到 0 dB，必须同时显式设为 `0`，避免重复衰减。

增益检查覆盖格式 / 样本数不变、补偿数值、非法参数拒绝和播放确认。设置生效后，用户再次实际按键并确认“更清楚，音量也合适”；该反馈支持本次修正改善了实际播放，不表示扬声器已达到电脑播放的保真度。
